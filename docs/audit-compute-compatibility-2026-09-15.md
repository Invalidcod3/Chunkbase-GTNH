# 计算兼容性与性能审计（2026-09-15）

后续状态：C1～C3 已修复，并增加按实测耗时判断扩张成本。见 [修复与验证记录](fixes-compute-compatibility.md)。以下保留修复前的审计证据和边界。

本轮重点检查自定义计算并行度、Worker 生命周期、GPU 计算初始化与取消，以及暮色底图的并行行为。仅新增审计脚本和报告，没有修改生产算法、缓存、设置或预览包。

## 已复现的问题

### C1 · P1：唯一计算线程启动超时后，地图重试无法恢复

位置：`dist/engine/compute-pool.js:7,79`，`dist/engine/worker-client.js:17`，`dist/engine/worker.js:11`，`dist/app.js:657`。

生产线程统一采用 15 秒启动期限，而 ready 消息要等所有函数包加载结束才发送。弱设备、慢速加载或某个函数包迟迟未完成时，唯一线程也会被标记失败并关闭；此时没有健康线程承接查询。取消 GPU 加速不能解决这一状态。

随后点击地图的重试按钮，只执行 retryPacks 和重新请求瓦片。retryPacks 对空线程列表返回空错误数组，没有重建计算线程，下一次查询继续报“没有可用的计算线程”。设置中的“重新尝试增加线程”会重建主线程，但地图的重试入口没有接通这条恢复路径。

复现使用同一 WorkerClient/ComputePool，将期限缩短为 20ms 并模拟未收到 ready：线程确实终止，存活数为 0，retryPacks 返回 []，后续查询仍失败；调用 retryCapacity 后恢复为 1 个线程。该实验验证超时后的状态机，不声称本机实际加载超过 15 秒。

建议：区分线程通信就绪与函数包就绪；不要把唯一线程的慢加载直接等同于并行扩张失败。地图重试应在零健康线程时先恢复主线程，失败时返回真实错误。

### C2 · P2：取消请求不能及时释放 GPU 初始化占用的计算队列

位置：`dist/engine/gpu-compute.js:42,62,123`，`dist/engine/worker.js:44`。

run 在 await ready() 前后检查取消，但 ready 内的适配器申请、设备创建、编译、自检不接收请求取消信号。Worker 又串行执行任务，所以切换世界或取消旧瓦片后，前端 Promise 虽能立即取消，同一线程内部的新任务仍需等待旧 GPU 初始化结束。

复现让实际 GpuCompute 的适配器申请暂不返回，随后取消请求：100ms 后内部 run 仍未结束；适配器申请结束后才抛出 CANCELLED。适配器申请本身有 10 秒超时，其他阶段各有自己的等待，不能把整个初始化理解成统一最多 10 秒。

建议：把设备预热与单个地图任务解耦，初始化未完成时让新查询走 CPU；保留当前 generation 隔离及独立自检，避免通过粗暴销毁正常线程来释放队列。

### C3 · P2：冷启动批量任务不能利用目标并行度，扩张时短批次反而变慢

位置：`dist/engine/compute-pool.js:18,91`。

线程池仅在新请求到来、且现有线程全部就绪并繁忙时扩张。启动期间到达的请求已全部交给主线程；ready 回调只更新数量，不重新调度待执行任务。因此，一次提交的首批任务不会在主线程就绪后自动分流。后续持续提交可以继续扩张，本问题不意味着永远只能运行一个线程。

使用真实预览函数包、生产的 15 秒就绪策略、Node 独立 Worker 传输，连续三轮测试暮色：每批 8 个 64×64、step=4 的查询，第一批后立即重复相同查询。以下为三轮中位数：

| 请求线程数 | 冷启动批次 | 冷启动实际线程 | 重复批次 | 重复批次结束时线程 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 359ms | 1 | 108ms | 1 |
| 4 | 353ms | 1 | 216ms | 2 |
| 8 | 339ms | 1 | 211ms | 2 |

关键证据是三轮均出现相同线程数量，并非几十毫秒的冷启动时差。短重复批次在扩张时还承担新引擎初始化、冷缓存和任务迁移成本。以上是特定查询负载的本地样本，不能据此推断所有设备、长时间拖图或大规模计算中多线程都更慢。

建议：线程池保留尚未派发的队列，在 ready 时逐步分流；扩张依据待处理计算量及启动成本，而不仅是 pending 数量。保留每个现有 Worker 的缓存，优先复用已完成初始化的线程。

## 尚需验证或继续优化的边界

- **高线程数缺少性能反馈。** `dist/gpu-settings.js:18` 采用设备提示限制数量，线程池遇到创建失败、启动超时或错误才降档。当前没有按查询延迟、吞吐或主界面卡顿自动让步。能够创建线程不等于这些线程有净收益；本轮未压测 64 个线程。
- **GPU 初始化按 Worker 重复。** 每个 Worker 有独立 GpuCompute，真正收到支持的查询后分别创建设备、编译内核、自检，并对首个实际内核查询做 CPU 全量对照。高并行度叠加 GPU 时可能产生重复初始化和资源竞争，但本轮没有真实 GPU 数据，不能量化损失。可评估独立 GPU 队列或受控预热，CPU 引擎与缓存保持隔离。
- **新旧版本混用保护不完整。** 新增 Worker 按相同 URL 加载代码；协议只检查地图数据类型、群系名称和请求 epoch，没有构建/函数包版本握手。在页面保持打开、服务器更新后再扩张线程的条件下，可能混用不同算法版本。源码路径支持此风险判断，本轮没有进行在线更新复现。建议使用不可变版本资源地址及版本握手，不能只依赖群系名称一致。
- **真实设备兼容性仍有验证空白。** Node 测试及整数内核对照不能证明所有浏览器/驱动均能编译 WGSL，也不能证明 GPU 比 CPU 快。产品已有运行时一致性检查和 CPU 回退，但仍需另行测量真实设备的首次可见时间、平移延迟和持续吞吐。

## 验证与限制

- 现有 Node 自动化测试：483 项全部通过。
- 本轮暮色批次：144 个查询，589,824 个输出像素；不同并行度及重复查询之间零差异。这是相互一致性检查，不是新增的 Java 原版校准。
- 已有独立 8 Worker 验证：6 个维度、9 个查询、2,907 个像素，与单线程 provider 对照零差异。该旧验证使用 WorkerClient 默认的“立即就绪”配置，验证结果隔离，但不覆盖生产冷启动调度。
- 新复现脚本：`node tools/audit-compute-compatibility.mjs`。
- 原始结果：`.test-work/compute-compatibility-audit.json`。
- 没有执行浏览器交互、实际 WebGPU 派发或高线程数内存压测；未发现新的计算结果错误，不代表所有输入或硬件都已覆盖。

建议先处理 C1 恢复路径，再处理 C2 取消等待和 C3 启动调度；之后用真实设备数据决定进一步提高线程数与 GPU 工作量是否值得。
