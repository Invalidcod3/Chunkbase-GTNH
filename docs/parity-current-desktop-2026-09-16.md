## 1. 高优先级：小行星资源预测未迁移

原项目新增 `AsteroidOrePredictor` 和 `AsteroidProspecting`，通过 `ProspectingService.ore()` 按有效维度定义区分普通矿脉与小行星，后者不使用普通矿脉网格。输出包含：

- `ASTEROID_SMALL` 与 `ASTEROID_VEIN` 两种类型。
- `asteroid.small:` / `asteroid.vein:` 资源身份及分别采集的材料列表。
- 独立随机选择得到的 X/Y/Z 中心、半径对应的大小，以及高度包围范围。
- 石材、大小矿选择和坐标随机流的正确分离。

网页 `dist/engine/prospecting.js:104` 的矿脉分支仍统一按普通矿脉的 3×3 区块网格筛选，结果为 `ORE_VEIN`、固定 `size=16`、区块中心 X/Z；缺少上述小行星分支。当前完整包的 `end`、`asteroids`、`kuiper_belt`、`mehen` 四个入口都接入了该旧资源实现。

本轮实际调用完整包资源配置：种子 0，矩形 `[0,512) × [0,512)`。这四个维度各返回 121 条 `ORE_VEIN`，全部在区块中心，均无中心 Y。这是网页当前输出的复现，不是与同范围游戏结果的数量对照。

更直接的接口证据：`dist/engine/resources.js:14` 仅允许普通矿脉类型和固定坐标/大小格式。将原项目测试所用形状的小行星数据（`ASTEROID_SMALL`、X=-258、Y=250、Z=364）传入当前校验，得到 **“无效矿脉预测”**。因此不能只加图层名称或图标，必须一起迁移配置采集、预测、结果接口、筛选和导出。

## 2. 高优先级：末地分区语义不同

网页按输入种子的“全新末地”重建中央区、HEE 岛屿与混沌岛避让，不读取已加载世界和末影龙历史。

最新版原项目 `AsteroidProspecting.effectiveDefinition()` 要求同种子的末地已加载，再通过原生 `getEffectiveDefForChunk()` 区分岛屿普通矿脉与虚空小行星。最新 `EndAsteroidPredictor.selectCurrent()` 也改用此分区及通用小行星预测，携带 Y；没有匹配的已加载末地时不会照常给出这批结构候选。

因此，相同种子并不保证两端结果相同。保留网页纯种子预览是合理能力，但应明确它与存档模式不同；不能靠更换图标或复用旧避让校准宣称两者完全一致。若要逐项对齐真实存档，需要本地只读连接或明确的存档状态输入。

## 3. 高优先级：导出缺失高度，跨维度文件仍可重名

- 新桌面版保留小行星中心 Y 到单点路标、CSV 与 JourneyMap。
- 网页 `journeyMap()` 除特定已记录出生点外仍使用用户填写的 Y，默认 64。绕过资源校验给它输入 Y=250 的小行星记录，本轮实际 ZIP 输出仍为 Y=64。这是独立的导出缺口，不表示网页已经能生成该小行星记录。
- 主世界和月球分别导出同种类、同 X/Z 的普通矿脉，本轮复现文件名和 ID 完全相同，仍有放入同一目录后覆盖的风险。旧 B1 尚未修复。

## 4. 采集与校准工具落后

当前原项目 `BiomeWorkerServer.java:40` 使用协议 25；网页维护工具 `tools/worker-query.py:29` 仍发送协议 21，`tools/collect-calibration.py:25` 也固定写旧协议来源。旧 B3 的差距已从 23 扩大到 25。

静态网页运行不依赖此协议，因此现有包仍可打开；但继续采集、验证最新原项目之前必须升级工具，并实际重新采集新字段，不能只修改报告上的协议号。

## 5. 其他已确认缺项与问题

| 项目 | 当前差异与影响 |
| --- | --- |
| 最近 N 个结构/资源 | 桌面 `RadialCoordinateLocator` 先完成所有更近区域再确认结果；网页按矩形分块扫描并截取，不保证最近 N 个 |
| 刷新后的地图缓存 | 桌面 `MapStorage` 有校验与容量淘汰的磁盘缓存；网页有内存缓存和偏好保存，尚无跨会话底图缓存 |
| 存档勘探状态 | 桌面可叠加 Visual Prospecting 已记录矿脉、枯竭和当前流体产量；网页只提供预测和初始产量，结果接口明确拒绝存档状态 |
| 实际世界准确性检查 | 桌面新增独立预测对照及验证报告，包含只读 Roguelike 选址检查；网页离线校准工具不能替代用户当前存档的验证 |
| JourneyMap 自动加入 | 桌面有单点路标及可选自动导入；网页仍以复制坐标、批量文件导出为主 |
| 隐藏结构占用上限 | 旧 B2 仍可复现：实际页面收集流程接收首片 20,000 个隐藏矿井后终止，第二片可见结构未扫描。属于合成密集负载的控制流复现 |

### 不应误报为缺项的内容

- 网页已实现出生点地形/洞穴重放估算，也已提供选择 `level.dat` 读取出生点的入口；缺少的是桌面与当前游戏世界的自动联动，不能再写成“没有出生点”或“完全不能读取存档文件”。
- 当前原项目文档说明其要塞菜单与地图仍存在两条预测线路。网页这两处使用相同的 RWG 基础公式。本轮以种子 `5942749603128060499` 复现两处均为 `(-592,816)`、`(-416,-944)`、`(1104,112)`，与原项目诊断中的 Worker 角点一致。不能为了“对齐”复制原项目已知菜单偏差；这些坐标也不是传送门房间。
- 已有暮色、扩展维度、地下流体和专属结构的旧校准不能被一概否定。本次明确定位的是新能力缺失和语义差异，并未完成全部算法的新版实机重校准。

## 建议开发顺序

1. 协议 25 的只读采集适配与新配置格式。
2. 通用小行星资源预测：类型、石材/矿物权重、X/Y/Z、大小及高度范围。
3. 明确末地纯种子预览和实际存档分区的边界；补对应对照数据。
4. 资源接口、导出高度与路标身份；修复隐藏结构计数。
5. 最近 N 个查询、跨会话缓存；游戏连接和存档验证作为独立能力推进。

这些工作不依赖新 UI 模板，可先完成计算与数据层。
