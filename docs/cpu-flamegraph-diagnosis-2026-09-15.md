# 核心 CPU 火焰图诊断

后续状态：原型已接入正式构建并重新校准，见 [CPU 优化替换记录](cpu-optimization-release.md)。本文火焰图与下述数据保留替换前的诊断基线；捕获时的源码快照保存在 `variants`，与目前运行代码可能存在行号差异。

结论：当前主要开销集中在 Java 转译引擎的长整数运算、主世界 CellNoise/群系混合，以及部分维度粗算和精算的重复工作。并行补测也复现了“CPU 消耗明显增加、等待时间改善有限”的暮色情况。已验证两种保持样本结果一致的局部优化原型；本轮没有将原型写入生产算法或已校准函数包。

## 采样方法与边界

- 机器：AMD Ryzen 7 7745HX，16 个逻辑处理器，约 31.2 GiB 可见内存；Node v24.19.0。
- 使用 V8 Inspector CPU Profiler，申请 1,000µs 采样间隔。操作系统实际采样间隔会有波动，统计按 timeDeltas 加权，不假设每个采样点恰好等于 1ms。
- 每种场景单独启动进程，加载当前完整预览中的真实函数包；地图先做小规模预热，再使用同一种子的未查询位置。正常缓存、分片及取消让步逻辑保留。
- 地图查询为 128×128 输出，比较 step=4 与 step=16；刷怪笼查询为 512×512 世界区域，包含邻近结构筛选。
- 火焰图宽度和表格占比均为**非 idle 的加权采样时间**，包含 GC。自身时间排除子调用，包含子调用的宽度不能相加当作独立开销。
- 这是实际 CPU provider 的隔离剖析，未录制浏览器主线程、绘图、Worker 传输或 GPU，也未对原 Amidst Java 客户端进行同条件计时。不能据此将原项目与网页之间的差距全部量化。

交互火焰图：`.test-work/cpu-profile-2026-09-15/flamegraphs.html`，支持选择场景、搜索、悬停和点击放大。该文件不依赖网络，可直接打开。

## 为什么 CPU 更忙，却感觉没有更快

使用当前生产线程池和真实独立 Worker，分别请求 1、2、4、8 个线程；每种设置先处理一批地图，再处理同种子的 8 个新区域瓦片。以下为第二批结果，step=16、每块 128×128。每档单次扫测，不是统计稳定的跨设备结论；线程池仍按当前规则逐步扩张，所以目标 8 的暮色在第二批结束时实际就绪 7 个。

| 维度 | 目标 / 实际就绪线程 | 首块返回 | 8 块全部完成 | 总 CPU 消耗 |
| --- | --- | ---: | ---: | ---: |
| 主世界 | 1 / 1 | 1,436ms | 12,359ms | 9,219ms |
| 主世界 | 4 / 4 | 1,880ms | 3,941ms | 10,922ms |
| 主世界 | 8 / 8 | 1,991ms | 2,150ms | 14,484ms |
| 暮色 | 1 / 1 | 263ms | 2,098ms | 1,406ms |
| 暮色 | 4 / 4 | 327ms | 682ms | 1,515ms |
| 暮色 | 8 / 7 | 339ms | 632ms | 2,577ms |

总 CPU 消耗是 process.cpuUsage 得到的进程线程累积 CPU 时间，包含引擎、JIT、GC、线程启动等开销；不是单线程时间或系统 CPU 占用百分比。

- 暮色目标 4→8：整批等待减少约 **7.4%**，总 CPU 消耗增加约 **70.1%**，首块返回还略晚。扩张的边际收益已经很低。
- 主世界目标 1→8：整批确实明显变快，但首块从 1,436ms 延长到 1,991ms。吞吐提升不能保证最先看到清晰地图的时间也改善。
- 这组测试复用了当前线程池和缓存，因此真实包含新线程初始化、独立引擎、冷缓存和调度成本。它没有把这几项逐一隔离，不能将增加的 CPU 全部归因于其中一种。
- 当前扩张估算主要比较启动时间与排队工作量，不能保证新增线程实际提高吞吐。后续应按维度、尺度和任务类型记录扩张前后的边际收益，并区分首个清晰瓦片优先与后台整批吞吐。稳定窗口内收益不足时停止扩张，避免仅因仍有排队任务就增加 CPU 消耗。

两维度、两阶段、四档位共 128 次查询，2,097,152 个输出像素；不同目标并行度之间结果一致。进程 RSS 也已记录，但受先前 Worker 的分配器保留影响，不将跨阶段 RSS 数字当作单个维度或单个线程的精确内存占用。

## 主要热点

| 场景 | 查询数 | 单次查询中位数 | 主要自身耗时，非 idle 占比 | GC 占比 |
| --- | ---: | ---: | --- | ---: |
| 主世界 step 4 | 20 | 126ms | CellNoise.valueNoise2D 20.4%；Long_shr 14.7%；Long_toNumber 10.0% | 5.0% |
| 主世界 step 16 | 3 | 1,143ms | CellNoise.valueNoise2D 16.2%；Long_shr 12.9%；createBlendChunk 8.9%；Long_toNumber 8.0% | 6.3% |
| 暮色 step 4 | 48 | 15ms | Long_create 39.0%；GenLayer.initChunkSeed 18.7% | 3.9% |
| 暮色 step 16 | 14 | 179ms | Long_create 42.2%；GenLayer.initChunkSeed 18.5%；GenLayer.nextInt 10.5% | 3.7% |
| 下界 step 16 | 4 | 631ms | Long_create 41.5%；HellVoronoiZoom 21.5% | 3.8% |
| 刷怪笼 512×512 | 6 | 551ms | 洞穴生成循环 13.5%；JavaRandom.nextFloat 13.5%；Long_create 12.5%；洞穴掩码导出 10.1%；Long_shru 10.1% | 5.3% |

缓存重复计时单独进行，地图同一查询中位数约 0.005～0.023ms，刷怪笼完整 provider 重复约 5.6ms。这里不含绘图和传输，说明命中后的引擎返回很便宜，不能据此证明所有场景的缓存命中率都足够高。

### 1. 暮色、下界：循环中反复构造固定长整数

暮色 `packs/twilight/selection.js:1208` 的 GenLayer 初始化种子，每轮都调用：

```js
Long_create(1284865837, 1481765933)
Long_create(4150755663, 335903614)
```

这些参数不变，但 `Long_create` 每次仍进行 BigInt 转换、移位、掩码和合并。下界的生成链有相同模式。洞穴随机数的乘数和掩码也被重复构造。生成代码中的长整数不是原 Java 的机器整数指令，存在可直接消除的转译开销。

优先方案：在生成/编译阶段将字面量 Long_create 常量折叠为等价 BigInt 常量。只处理可静态证明的常量表达式，保留动态种子、64 位溢出和有符号语义。正式接入应修改构建流程，并重新跑原实例校准，避免手工维护编译产物。

### 2. 主世界：CellNoise 对最终只保留低 31 位的值做了整套长整数运算

位置：`packs/rwg/selection.js:3564`，调用者 noise/border 分别在 3522、3488 行。

噪声函数最终以 `& 2147483647` 取低 31 位，再除以 2^30。该多项式的低位结果可以用 `Math.imul` 等价计算；种子必须先以 `BigInt.asIntN(32, seed)` 精确提取低 32 位，不能直接把完整 64 位种子转成 Number。末尾双精度除法和返回值保持原语义。

当前每次 CellNoise 搜索还检查 5×5 邻域，邻近点反复调用该函数，因此局部热点收益会被放大。消除这里的 BigInt 开销后，再重新剖析 createBlendChunk、插值数组和缓存查找，按新的占比决定下一步，不先改所有缓存容器。

### 3. 粗算不一定少算：GenLayer 的底层区域几乎没变

位置：`dist/map.js:395` 的预览查询，`dist/engine/twilight-provider.js:49` 和 `dist/engine/extra-provider.js:36` 的区域生成/降采样。

暮色和下界会先生成底层连续区域，再抽取需要的点。把输出从 128×128 减为 64×64、同时把 step 翻倍，覆盖的世界区域仍近似相同，昂贵的底层生成量没有按输出像素降为四分之一。接着精算时，当前输出栅格缓存无法复用不同采样参数下的底层中间结果。

同区域、三种种子、交替执行顺序的独立计时：

| 场景 | 直接精算 | 仅粗算 | 粗算＋精算 | 总耗时/直接精算 |
| --- | ---: | ---: | ---: | ---: |
| 暮色 step 4 | 15.5ms | 15.2ms | 31.4ms | 2.03× |
| 暮色 step 16 | 261.4ms | 264.1ms | 514.0ms | 1.97× |
| 下界 step 4 | 77.1ms | 76.6ms | 154.5ms | 2.00× |
| 下界 step 16 | 958.6ms | 686.9ms | 1,605.4ms | 1.67× |

优先方案：保留通用的渐进显示调度，但让 provider 提供粗算成本信息。对不能明显减少生成工作的路径，直接生成精算瓦片，等待期间复用已有画面。后续可设计单次底层生成同时产生预览和最终结果，或增加明确限定的中间层复用；需要额外验证缓存生命周期、坐标对齐和取消后结果隔离。

注意：step 16 的 128×128 瓦片覆盖面积是 step 4 的 16 倍。主世界跨越的区块更多，GenLayer 要生成的底层区域也更大。因此相同输出像素数不意味着相同计算量；缩小地图后反而更慢有算法层面的原因。

## 隔离原型验证

没有改生产文件。把编译模块复制到本次诊断目录，对副本应用变换，沿用相同 provider 和缓存实现；三种种子包含有符号 64 位两端，交替执行基线和候选版本。以下是各版本三次计时的中位数之比，属于局部样本，不是浏览器整体加速倍率。

| 原型 | 场景 | 基线 | 候选 | 加速比 |
| --- | --- | ---: | ---: | ---: |
| 固定 Long_create 常量折叠 | 暮色 step 4 | 30.6ms | 15.4ms | 1.99× |
| 同上 | 暮色 step 16 | 263.5ms | 107.6ms | 2.45× |
| 同上 | 下界 step 16 | 911.9ms | 493.9ms | 1.85× |
| 同上 | 主世界 step 4/16 | — | — | 约 1.00×，没有明显收益 |
| CellNoise 低位整数等价改写，另含常量折叠 | 主世界 step 4 | 200.7ms | 124.2ms | 1.62× |
| 同上 | 主世界 step 16 | 1,537.7ms | 949.2ms | 1.62× |

正确性检查：50,000 组 CellNoise 输入、344,064 个地图像素比较、3,145,728 个洞穴掩码单元均一致。洞穴常量折叠的 16 区块掩码测试中位数约 39.4→30.0ms，约 1.31×；该值不能当作完整刷怪笼查询的提速。原型尚未完成全维度、浏览器和完整原实例校准，不应直接替换正式函数包。

## 建议开发顺序

1. **常量折叠进入生成流程。** 改动集中，已有显著样本收益；覆盖暮色和多个 GenLayer 维度。验收要求包括极端种子、负坐标、边界、全部已保存校准以及浏览器编译运行。
2. **按成本选择粗算路径。** 先避免无收益的第二次生成，不调整已有结果缓存的键或淘汰策略；用首个清晰瓦片时间和完整视口完成时间验收，不能只看粗图出现时间。
3. **CellNoise 精确整数优化。** 将数学上等价的低位运算纳入受版本约束的编译适配，重新校准主世界地图、地形相关结构和刷怪笼。
4. **再处理洞穴随机数和数组转换。** 火焰图表明随机数长整数包装、对象数组导出均占有比例。可评估 48 位分段整数状态和直接 TypedArray/位掩码输出；保留拒绝采样、浮点与洞穴生成语义。这一项尚未验证完整实现收益。
5. **优化后重新剖析，并改用边际收益决定线程扩张。** 增加首个清晰瓦片时间与吞吐指标；把初始化阶段、粗算和精算分开统计，避免廉价批次继续扩张。再决定是否投入 Wasm 或 GPU。当前 GPU 路径主要覆盖末地与部分结构候选，未覆盖此处的 GenLayer、RWG CellNoise/混合和洞穴主体。它们也是 CPU 高占用仍明显的原因。绘图主线程、浏览器线程竞争和真实显卡收益仍需独立浏览器录制。

## 原始资料与复现

目录：`.test-work/cpu-profile-2026-09-15/`。

- 六个 `*.cpuprofile`：原始 V8 CPU profile，可导入支持该格式的性能分析器。
- 六个同名 JSON：环境、请求、耗时、结果哈希、函数包哈希。
- `summary.json`：加权自身时间及包含子调用时间。
- `flamegraphs.html`：离线交互火焰图。
- `experiments.json`、`variants/`：隔离优化原型及配对结果。
- `progressive-cost.json`：同区域粗算/精算开销。
- `parallel-efficiency.json`：当前生产线程池的 CPU 消耗、首块延迟和整批吞吐。

复现命令：

```text
node tools/profile-core.mjs
node tools/summarize-core-profile.mjs
node tools/experiment-cpu-hotspots.mjs
node tools/profile-progressive-cost.mjs
node tools/profile-parallel-efficiency.mjs
node tools/summarize-core-profile.mjs
```

采样结果用于定位热点，隔离实验用于检验优化方向；二者工作负载和预热不同，表格耗时不应跨实验直接相减。
