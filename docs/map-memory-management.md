# 大范围地图的内存管理

本轮调整地图资源和空闲线程的生命周期，保持群系生成算法、采样间隔、Provider 缓存键和容量不变。

后续加入的 [算力分配](compute-allocation.md) 在现有线程总量内分配出图与精化，不额外创建一套计算池，继续沿用本文的内存管理。

源码检查发现：地图原来按 256～4096 块的数量上限保留瓦片，每块同时保留群系数组与绘图画布；旧缩放级别离开视野后仍占有画布，GPU 开启也会先创建瓦片画布。计算池仅在降低档位或失败时回收额外线程，长期空闲时仍保留每个引擎及其缓存。RWG 自身的群系点缓存已有 4096 条清理阈值，并非无限增长；不能仅凭任务管理器的内存上升判断泄漏。

## 新策略

- 当前视野的目标级别瓦片优先保留，不因历史预算不足被反复淘汰、重算。
- 历史瓦片采用字节预算：按当前可见块数调整，范围为 1～8 MiB；设备内存提示不超过 2 GiB 时，历史预算最多 2 MiB。另限制最多 256 个历史条目。预算包含样本数组、画布 RGBA 大小和每条 256 字节的估算开销。
- 离开视野先把画布尺寸置零并释放引用，保留群系数组供返回时复用；返回视野时才重新配色，不重新查询生成器。预算不足时优先保留仍覆盖当前视野的旧缩放级别，其余按最近使用顺序保留。
- 缩放和移动时立即清理，不必等下一块计算完成；预览被精算替换、切换世界时同时释放旧画布和 GPU 纹理。离开视野的失败记录也及时清除。
- GPU 模式仅持有样本数据和实际可见瓦片纹理，不提前创建 CPU 瓦片画布；GPU 回退后按需重建。改配色也推迟到绘制可见瓦片时处理。
- 额外计算线程持续空闲 60 秒后释放，保留主线程与其缓存。正在执行、初始化以及等待分配任务时不回收；请求的并行度保持不变，有任务时重新按需创建。释放的额外线程下次会重新加载引擎，因此长时间停顿后的并行启动有一定成本。

当前可见瓦片使用的内存单独保障，所以历史预算不是整页或浏览器进程的硬上限。生成器工作区、主画布、GPU 驱动、对象实际大小和浏览器回收时机会影响总占用；不能保证操作系统立即显示等比例下降，也不强制触发垃圾回收。

## 测试与测量

`node tools/benchmark-map-memory.mjs` 重放 1920×1080 视口、28 轮拖动与 4/8/16/32 采样间隔缩放。按相同 RGBA 和数组字节规则计算，旧策略瓦片存储峰值为 36,861,440 字节，新策略为 17,728,768 字节，降低约 51.9%。这属于瓦片资源预算对比，**不是浏览器堆、显存或整页 RSS 实测**。每轮检查当前完整瓦片仍在缓存，采样分辨率没有降低。原始记录在 `.test-work/map-memory/comparison.json`。

501 项自动化测试通过，新增覆盖历史预算、可见瓦片保护、释放画布后的数据复用、GPU 回退按需重绘、离屏纹理释放、忙线程保护、空闲线程释放与重新扩张。完整本地包通过 8 个真实独立计算线程、6 个维度、2,907 个像素的一致性检查，42 个底图和 41 个资源维度路由验证通过。本轮未做浏览器交互、堆快照或真实 GPU 驱动测试。
