## 已复现的问题

### F5 · P1：强制粗算让暮色默认级别加载显著变慢

位置：[MapView](../dist/map.js)，331、345 行；[暮色 Provider](../dist/engine/twilight-provider.js)，22–35 行。

当前所有有底图的新瓦片都会先请求更大间隔的预览。默认级别的暮色精算为 `128×128, step=4`，可走 GenLayer 批量路径，每 16 行调用一次，共 8 次；预览为 `64×64, step=8`，却落入逐点查询路径，共调用生成器 4,096 次。请求数量更少并不意味着内部计算更少。

同一种子 `0`，覆盖相同世界区域，分别重新配置 Provider，先测试精算再测试预览：

| 左上角 X / Z | 直接精算 | 粗预览 | 精算 / 预览调用次数 |
| --- | ---: | ---: | ---: |
| 0 / 0 | 60 ms | 803 ms | 8 / 4,096 |
| 1,536 / 0 | 21 ms | 585 ms | 8 / 4,096 |
| −2,048 / 0 | 14 ms | 521 ms | 8 / 4,096 |

预览点与精算中的对应点逐一相同，问题是重复运行生成链的成本，而非结果错误。每个位置只做了一组本地测试，包含 JIT、缓存和其他测试负载影响，不将比值当作稳定跨设备指标。

建议：保留通用粗细状态机，但由 Provider 声明合适的采样方式。暮色可以先批量计算有界的连续栅格再抽样，也可在默认级别直接精算；不要为所有生成器强制指定更大 step。固定单群系及足够快的维度同样允许直接完成。自适应耗时阈值可后加，先消除这个确定性的退化。

验收：暮色 step=1、2、4、8、16 的批量和稀疏结果保持一致；正负坐标和边界通过；预览不能仅因更换 step 而触发数千次重复生成。性能对比应覆盖首批可见结果和完成整个视野两个指标。

### F6 · P2：结构层仍会在合法的大视野整体失败

位置：[应用查询](../dist/app.js)，247–280 行；[RWG 结构](../dist/engine/rwg-structures.js)，6 行；[暮色结构](../dist/engine/twilight-provider.js)，41 行；[通用边界检查](../dist/engine/native.js)，5–19 行。

F1 修复只把资源查询分批，结构仍然一次请求整个视野。画布 1,920×900、比例 0.125 对应 `15,360×7,200 = 110,592,000` 方块，超过多个结构 Provider 的 `67,108,864` 上限。真实入口复现中，主世界、暮色、月球和下界都报“查询范围过大”。界面随后清空该层结果；结构导出复用同一种完整视野请求，因此同样受影响。

建议：增加独立的结构区域查询器，保留 Provider 单次上限，分批、去重、增量显示并提供明确进度。不能简单提高面积上限；不同结构需要保留邻域判定范围，例如刷怪笼候选依赖附近结构。输出点按原始视野裁剪，区域边界不应改变候选结果。

验收：主流画布和全部允许缩放级别不整层失败；整批与分批结果在可比较区域一致，负坐标及跨区域没有重复或漏点；导出达到上限后停止后续查询。

### F7 · P2：旧视野任务占据 FIFO，新底图仍要等待

位置：[Worker](../dist/engine/worker.js)，12–24、31–44 行；[应用](../dist/app.js)，247–280 行；[MapView](../dist/map.js)，247–248、325–343 行。

普通拖动和缩放只更新视野，结构结果通过 revision 失效；只有全局 reset 才会真正清空 Worker 队列并中止运行任务。真实 Worker 调度源码在受控 Provider 下的执行顺序仍是：

`旧视野正在扫描 → 旧视野已排队扫描 → 新视野底图`

MapView 的最多 4 个待处理请求也包含已经离开屏幕的旧瓦片。现有“预览优先”只影响新提交的瓦片顺序，不能改变已经进入 Worker 的任务优先级。拖动越频繁、结构扫描越昂贵，差距越明显。

建议：给请求增加用途和视野代次，分别管理底图、可见标记和显式导出任务。合并或取消过时的视野查询，可见底图优先；导出由独立取消控制管理。保持单个 Provider 状态串行安全，不能为了抢占而并发改写共享的种子/生成器对象。先完成取消、合并及有界计算片段，再评估多个 Worker。

验收：快速拖动后，下一批优先处理当前可见区域；旧结构请求不继续排满队列；主动导出不因普通平移被误取消；不同种子结果不混入。取消响应时间需要真实浏览器测量。

### F8 · P2：隐藏结构图层后仍会发起昂贵扫描

位置：[refreshStructures](../dist/app.js)，247–275 行；结构显示开关约 429–439 行。

显示开关只改变 `view.showStructures`，而视野回调仍无条件请求结构。使用真实 `refreshStructures` 函数和界面桩，把 `markerMode='STRUCTURE'`、`showStructures=false` 后触发视野更新，依然发出一次 `predictStructures`。

用户关闭结构希望只看底图时，结构计算仍占用同一 Worker；大视野还会收到看不见的图层报错。如果之前启用了节点或刷怪笼等扫描，这个影响更明显。

建议：结构隐藏时停止自动结构查询并取消相应视野任务，重新显示时按当前视野加载。显式结构导出仍可按其独立语义运行。此修复应与 F7 的按用途取消一起实现，不能直接 reset 全部任务。

### F9 · P2：异步 PNG 保存可能使用另一世界的文件名

位置：[PNG 保存](../dist/app.js)，641–656 行，尤其是 654–655 行。

`toBlob` 生成的是调用时的画布，但回调中的文件名使用届时全局 `dimension`、`seed`。复现：保存 `overworld / 0` 的画面 → 在回调前切换到 `moon / 123` → 输出文件名变为 `amidst-moon-123.png`。图片仍属于旧世界，标识却属于新世界。已有 PNG 测试把 `toBlob` 设为同步，未覆盖此窗口。

建议：开始保存时捕获完整导出快照，文件名也从同一快照生成。验收应使用延迟回调，同时覆盖切维度、换种子及连续保存。此项是异步状态复现，尚未测量实际浏览器中该窗口持续多久。

## 更新后的开发顺序

### 第一批：稳定加载与交互

先处理 F5，再将 F7、F8 一起处理，并补 F6。F9 是小而独立的状态修复，可以同批完成。

通用机制应当统一任务状态、取消、缓存及完成语义；具体计算粒度根据生成器能力选择。保留 64×64 作为适用生成器的默认预览策略，允许批量抽样或直接精算。这里暂不承诺中心精算、多 Worker 或 WASM 的收益，应在调度问题解决之后用数据决定。

测量至少包括 RWG、暮色、末地和一个固定群系维度；记录首批可见时间、完整视野时间、取消后的恢复时间、队列长度及缓存占用。除默认画布外，覆盖 1,920×900、低缩放级别、连续拖动和快速切图层。测试集增加延迟 Worker、过时队列及异步导出场景，不能只核对算法输出。

### 第二批：资源能力及维度目录

资源算法已经校准到 41 个维度，目前菜单/私有包入口仍只有 11 个维度。下一项高收益功能是环境驱动的维度目录：同时调整 `catalog.js`、配置校验、包注册和构建器，按实际环境 ID 开放其余具备资源能力的维度。没有真实底图的维度要明确显示“仅资源/结构可用”，不能填充伪造地形。

资源交互补类型选择、矿脉高度范围、流体最佳区块/全部区块选择、独立导出取消。20,000 个位置上限之前的筛选策略需要明确：当前文本筛选仅针对已收集的地图结果，可能无法找到尚未扫描的外围资源。该限制已经显示为“部分结果”，不应误当作完整视野没有匹配项。

### 第三批：补桌面功能

优先世界出生点，再逐个接入下界、Io、Pluto 等真实复杂底图及适用维度。出生点要移植原 Worker 的规则，不把 `(0,0)` 当作世界出生点。保留既有 RNG、候选语义、原版要塞简化范围和环境校准要求；不重复开发已经对照通过的矿脉、流体及已接入结构算法。

存档记录、耗尽状态和当前流体量继续属于首版范围之外，不能作为当前纯种子预测的缺陷。

### 与上述工作同步：交付、状态提示和验收

- 为默认包与完整私有包标明版本、能力清单及环境指纹，完善可重建步骤和本地启动入口。`file://` 不能直接运行的问题尚未通过计算优化解决；优先提供启动器及说明，不建议为双击 HTML 重写模块和 Worker 架构。
- 加入明确的失败/重试状态。现在瓦片三次失败后仍未完成，加载提示无法区分继续计算和已经停止重试；需要产品层面的恢复入口。
- 修正文案中的能力描述，例如英文暮色仍被称为 Single-biome preview。历史文档保留历史结论，但必须引导到本报告。
- 完成浏览器拖动/缩放、慢任务取消、触屏和高像素密度屏幕验收；JourneyMap 仍需游戏内导入检查。本轮不将数值校准视为这些验收已经完成。
