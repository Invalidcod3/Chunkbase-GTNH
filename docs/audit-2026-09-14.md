## 已复现的代码问题

### F1 · P1：正常大屏视野超过资源查询上限，矿脉／流体层整体失败

位置：`dist/app.js:227`、`dist/engine/prospecting.js:73`、`dist/engine/prospecting.js:85`。

地图把整个可见区域作为一次资源请求发送，而预测器限定面积为 16,777,216 方块，并另限 65,536 个扫描单元。上限本身合理，但界面没有分块处理。

复现使用实际 MapView 坐标计算和真实资源配置：

| 画布尺寸 | 比例（屏幕像素／方块） | 结果 |
| --- | --- | --- |
| 1920×900 | 默认 0.25 | “查询范围过大，请放大地图或缩小导出范围” |
| 1280×600 | 默认 0.25 | 成功，返回 5,350 个矿脉候选 |
| 1280×600 | 缩小至 0.125 | 同样报范围过大 |

例如第一项对应 7,680×3,600 方块，总面积 27,648,000。失败后 `refreshStructures` 清空资源结果；导出也走同样的单次大范围查询。流体模式共享面积检查，因此同样受影响。

建议：按固定世界区域分块查询、去重并增量显示；保留每个请求的安全上限，对低缩放级别制定可见密度策略。导出独立分批，达到数量上限后停止后续扫描。

验收：常用画布和允许的缩放级别不出现整层失败；跨零、负坐标和跨流体田边界的分块结果无漏点或重复；切换地图后旧结果不会回填。

### F2 · P2：暮色群系 JSON 导出没有满足 4 方块采样对齐要求

位置：`dist/app.js:544`、`dist/app.js:558`、`dist/engine/twilight-provider.js:23`。

导出器直接使用当前视野左上角，并根据视野尺寸选择 step。暮色在 `step=4` 时要求 X/Z 都是 4 的倍数，而拖动后的左上角通常不满足此条件。

复现：X 范围 `[1,1281)`、Z 范围 `[1,601)` 的导出参数为 `x=1,z=1,width=320,height=150,step=4`，实际暮色生成器入口抛出“暮色四分之一底图须对齐 4 方块网格”。普通地图瓦片总是对齐，因此现有瓦片测试没有覆盖这个交互路径。

建议：明确导出栅格与请求视野的关系，对齐采样原点并正确记录实际范围；或者让 Provider 支持任意原点的该档采样，保持原图层语义。

验收：任意正负坐标拖动后都能导出；输出的原点、step、尺寸与像素实际位置一致；涵盖 step=1、2、4、8。

### F3 · P2：无效种子后切换维度，显示状态和查询状态分离

位置：`dist/app.js:201`、`dist/app.js:356`；模式切换 `dist/app.js:360` 具有相同的先修改状态再校验顺序。

维度事件先更新全局 `dimension`，随后 `loadWorld()` 校验种子。如果用户正在编辑的种子无效，函数提前返回，没有更新 MapView，也没有增加 worldRevision 或取消旧请求。

用当前源文件中的真实事件函数执行最小界面复现：末地已载入 → 种子输入框改为无效文本 → 选择月球，结果是下拉框／后续结构请求维度为 moon，而 MapView 仍为 end，worldRevision 仍为 0。随后拖动或导出会基于不一致的状态工作。

建议：把正在编辑的种子与已经生效的世界状态分开；校验新状态成功后再一次性提交维度、种子、模式和配置，并统一取消旧请求。失败时保留一致的旧状态。

验收：空值、超出 long 范围等输入下切换维度／模式，底图、标记、标题、导出元数据始终属于同一已生效世界。

### F4 · P2：允许跳转的世界边界与整块瓦片请求范围冲突

位置：`dist/map.js:317`、`dist/engine/rwg-provider.js:65`；暮色 Provider 也会校验整张瓦片的范围。

相机允许到达 X=29,999,000，视野裁到 ±30,000,000，但取图仍发出完整 128×128 瓦片。边缘瓦片越过 Provider 的有效坐标限制，整块被拒绝。

复现：画布 1280×600、比例 0.25、相机 X=29,999,000，最后一个瓦片请求为 `x=29999616,width=128,step=4`。加上采样偏移，末像素到 30,000,126，超过 RWG 的 29,999,983 限制，报“RWG 底图请求超出有效范围”。重试不能修复该确定性错误；可见有效区域也缺图，PNG 的底图完成检查无法通过。

建议：统一各 Provider 的可用边界，裁剪边缘请求并在绘制层表示边界外区域，或按当前视野尺寸限制相机移动。

验收：四条边及四个角、各缩放级别能显示边界内区域，没有重复无效请求，并能完成 PNG 导出。

## 建议的后续开发顺序

1. **先修可用性缺陷。** 处理 F1–F4，将这些跨模块复现加入回归；不只是增加预测算法的固定样本。
2. **开放剩余资源维度。** 将硬编码的 `catalog.js` 目录、`validateConfig()` 维度白名单和构建器生成注册信息一起调整。当前函数包只能增强已有菜单项，单改菜单不够。维度 ID 应来自当前环境；沿用桌面“有资源或 POI 才显示”的规则。此项可以复用已校准的数据，无需等待复杂底图全部完成。
3. **补桌面已有的资源操作。** 目前仍是名称／材料文本搜索；补当前维度的类型下拉选择、矿脉 Y 范围、每个流体田最佳区块／全部区块选项、分批导出、数量上限提前停止和独立取消。记录／耗尽筛选随未来存档功能实现。现有 `filtered.slice(0, limit)` 发生在完整查询之后，不能节省预测成本。
4. **改善任务调度。** Worker 当前串行 FIFO；视野变化只让旧结果失效，没有按新视野淘汰旧结构任务。昂贵扫描仍可能占住队列。建议增加视野任务合并、优先级和取消，使可见底图优先，避免重复计算；以实际浏览器性能测试验收。本机 Node 的单张 128×128、step=4 RWG 瓦片冷算约 1,225ms、缓存 3ms，不能据此推断整个首屏已足够快。
5. **继续功能移植。** 出生点、下界复杂底图、Io／Pluto 及其余适用维度，逐项保留原随机数语义并制作独立样本。不要扩大未校准版本的支持声明。
6. **完成交付与文档。** 默认 `dist/packs/registry.json` 为空，默认 ZIP 与私有完整预览的能力不同。建立清晰的包类型、环境指纹、能力清单、版本标识及可重建流程；按项目现有 NOTICE 清单处理公开分发材料。更新 `architecture.md` 中“资源函数包尚未接入”等过期描述，明确 `offline-development.md` 只是历史记录。
7. **做浏览器和游戏端验收。** 覆盖维度／种子／模式快速切换、大屏与小屏、触屏、英文状态提示、慢计算取消、PNG 与标记完整性、JourneyMap 实际导入。当前英文提示还会把已接入的暮色错误称作 Single-biome preview，部分错误和辅助标签仍固定为中文。

对于 PNG，当前 `isFullyLoaded()` 只检查群系瓦片，`loadedBounds` 没有被用于导出完成判断。应在验收中检查结构／资源仍在计算时是否生成缺标记的图片，并为图层完成状态制定明确规则。
